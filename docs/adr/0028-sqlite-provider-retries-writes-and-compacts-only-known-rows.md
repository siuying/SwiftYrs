# SQLite provider retries failed writes and compacts only the rows it knows

`SQLiteProvider` still writes each observed update synchronously inside the document's update observer, so existing callers see an update on disk when their `write` returns. A failed write no longer drops the update. Observed updates enter an in-memory pending queue with a sequence number, and every write attempt writes the whole queue in one transaction, oldest first. The next observed update and `flush()` retry it. Each attempt yields one `SQLiteWriteResult` per update, and a failure still goes to `errors`. Writes are serialized by a lock, so the queue reaches the store in observed order. The auto-compaction row count runs inside the same transaction as the inserts. If it ran after the commit and failed, updates already on disk would stay pending and be written twice, as rows compaction never removes.

Auto-compaction and the async API run on one serial queue per provider. `flush()` writes the queue there and then waits for that queue to drain, so it also waits for an auto-compaction that a write scheduled. `close()` stops observing, flushes, and only then releases the document name and finishes the streams. It throws `SQLiteFlushError` with the unsaved update bytes after closing rather than leaving a half-closed provider. The teardown runs once as a shared task, so concurrent and later `close()` calls return only after the document is released, as in ADR-0027. A synchronous `compact()` runs on the caller's thread, outside the background queue. So `close()` sets a closing flag, after which `compact()` throws `destroyed`, and then joins the compaction lock before releasing the document. A compaction admitted earlier therefore finishes first, and none can write a snapshot after `close()` returns, for example over a document the app has just removed. `compactAndWait()` checks the flag and queues its work under the same state lock, so an admitted one runs ahead of the close. `destroy()` keeps its immediate, non-waiting behaviour. Its synchronous name could not gain an `async` overload: Swift prefers the async overload in async contexts and would reject existing un-awaited calls. For the same reason the awaitable compaction is `compactAndWait()` beside the existing `compact()`.

Compaction used to delete every row up to the store's current maximum ID. Another connection could append rows, or compact and replace them, before that query ran, and the provider's snapshot does not contain those rows. So the provider now tracks the row IDs it loaded or wrote, and compaction deletes exactly those, in the same transaction that appends the snapshot. Rows written by anyone else stay. A stale compaction can then only add a redundant snapshot, which loading merges harmlessly. A compaction generation would detect that another session had compacted, but it would still have to delete rows by ID to stay safe against plain appends, so tracking IDs alone is enough.
