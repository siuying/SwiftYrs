# One CloudKit zone per store holds many documents

`CloudKitRecordCodec` mapped one document to one zone (`swiftyrs.<b64(documentName)>`), and `CloudKitSyncStore` routed every engine callback by zone to exactly one provider. With subdocuments (ADR-0024) a consumer holds one root document plus one subdocument per page, so that mapping costs a zone, a change token, and a startup fetch per page. CloudKit does not ask for it: a zone is the atomic-commit, change-token, bulk-delete, and sharing boundary, and all four belong to the store's dataset, not to one document.

So the codec now takes a zone name at construction — `CloudKitRecordCodec(zoneName:assetDirectory:)`, the wiki app passing its vault UUID — and every document of the store lives in `swiftyrs.<enc(zoneName)>`. `zoneID(forDocumentName:)` is deleted rather than deprecated. This breaks records written under the old mapping: they are not readable, and the first sync after upgrading re-seeds the zone from a snapshot (local SQLite state is untouched). The library is pre-1.0 with no known deployments, and carrying both mappings would double the routing paths and the test matrix for a consumer that does not exist. A `(documentName) -> zoneName` closure was rejected for the same reason: it invites many-zone layouts nobody needs to route or test.

Record names carry their document: `doc.<enc(documentName)>.incremental.<clientID>.<from>.<to>` and `doc.<enc(documentName)>.snapshot`. The document must be recoverable from the name alone, because a deleted-record callback delivers only a `CKRecord.ID` — no fields. `<enc>` is the URL-safe base64 already used for zone names, which never contains `.`, so splitting on `.` is unambiguous. The `documentName` field stays on the record and decoding fails with a typed error when the name disagrees with either the field or the record type, so a malformed or forged name fails into the error stream instead of applying an update to the wrong document or being read as the wrong shape.

CloudKit rejects a record or zone name over 255 characters by raising an Objective-C exception, which Swift cannot catch, and encoding inflates a name by 4/3. Length is therefore checked before CloudKit sees it — but once per document, not once per record: `codec.documentKey(_:)` is the only place that can fail, and a `CloudKitDocumentKey` is the proof that lets every record-ID builder be non-throwing. A provider takes its key at construction, so an unusable name fails at setup rather than at the first flush, and no inbound or GC path has to treat "name too long" as a possible outcome.

`CloudKitSyncStore` keys its provider registry by document name and groups each fetched, sent, and record-to-save callback by the document parsed from the record name. A provider still sees only its own document's records, so `CloudKitProvider`, `SnapshotWriter`, `DrainSetManager`, and compaction are unchanged — every record ID they build already passes a `documentName` through the codec.

Routing by document exposes a hole the zone-keyed router hid: `CKSyncEngine` fetches a zone whether or not a provider is attached, and the old `dispatchFetched` dropped un-owned records while the change token advanced. With lazy per-page providers that silently loses remote edits. The store therefore spools fetched changes, persisted through `CloudKitMetadataStore` under a reserved namespace, and drains them into the provider in arrival order.

Every fetched change takes that path, not just the ones with no provider attached. Two paths would mean two orderings to reconcile and a flag to say which one a document is on, and the live path would keep the original hole in miniature: a change applied straight from the callback is lost if the process dies mid-apply, because the token has already moved. One queue makes arrival order a property of the data instead of the code, and the branch disappears. A batch is dropped only after the provider has applied it, and entries are removed by sequence number so a snapshot coalescing the queue during a replay cannot shift what gets dropped. Replaying after a crash is harmless: yrs updates are idempotent and commutative.

Requiring every provider before `start()` was rejected: it defeats the lazy loading that motivates subdocuments. The spool has no size cap in v1 — dropping the oldest entry is wrong for CRDT updates, and the correct degrade is forcing a snapshot fetch — but a fetched snapshot drops the spooled incrementals its state vector covers, which bounds a page that is synced often and never opened.

The spool holds decoded payloads rather than `CKRecord`s. An asset-backed record's file is only readable while the fetch callback owns it, so the bytes have to be taken then; and re-encoding a record for replay would write a fresh asset file that nothing deletes, only for the provider to decode it straight back. The provider's inbound entry point therefore takes payloads, and each set of bytes is converted once.

Removal comes at two grains because `CKSyncEngine` has no query path. `removeZone()` deletes the zone with everything in it and is exact; it is the consumer's "delete the vault". `removeDocument(named:)` deletes the records in a persisted per-document registry of known record IDs, updated on sent-saved and fetched-modified/deleted events, and is therefore best-effort: a crash between the server accepting a record and the registry write leaves an orphan, which the next snapshot cycle's GC collects. Both are documented as such rather than pretending the registry is authoritative.

Clearing local state at zone grain needs to know which documents have any, which the record registry cannot answer — a document may have a drain set and no records yet. The store keeps its own persisted index of document names, joined on a provider's first attach or a document's first fetched change, and removal walks that.

Removal and attachment are mutually exclusive: a document being removed rejects an attaching provider, and an attached provider rejects removal. Otherwise a provider starting during the awaits inside a removal would have the state it just created cleared underneath it. Every per-document metadata mutation is read-modify-write, so the store serializes all of them behind one lock; concurrent engine callbacks would otherwise lose each other's registry writes and leave records nothing knows to delete.

All of a store's documents now share one zone's record-count limits. Snapshot compaction (ADR-0023) keeps each document's record count near one snapshot plus a short incremental tail, so the practical ceiling is the number of documents, and there is no hard limit worth encoding in the library.
