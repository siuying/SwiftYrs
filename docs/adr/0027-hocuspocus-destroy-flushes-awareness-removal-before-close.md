# Hocuspocus destroy flushes the awareness removal before closing

`HocuspocusProvider.destroy()` is an awaitable, terminal teardown that follows `destroy()` in @hocuspocus/provider 4.7.0. It stops awareness checks and inbound processing, detaches the connection, and closes observer ingress. It then waits for callbacks that have already started and clears local awareness with origin `"provider destroy"`. It waits for every queued frame and the final awareness update to be written before closing the socket. Afterwards it finishes the event streams. The teardown runs once as a shared task, so concurrent callers return only after it completes. Later calls, `disconnect()` and `connect()` do nothing. `disconnect()` stays a temporary disconnect. It closes immediately, discards queued messages and keeps local presence for the next `connect()`, as a bare `disconnect()` does in JavaScript. A completed write means the frame was handed to the socket. It does not confirm that the server or peers applied it.

Each connection has a generation and its own outbound sender. A sender is a locked queue drained by a single writer task, so frames are written one at a time in order. Discarding a sender, on `disconnect()` or an unexpected drop, closes it immediately. Queued frames are dropped, and a frame the writer has not yet handed to the socket is dropped too. `destroy()` instead finishes the sender: it stops accepting frames and waits for the queue to empty. Work that suspends checks the connection's generation and the lifecycle when it resumes, before queueing anything. This covers token retrieval during the handshake, a token request from the server, transaction retry waits and each receive. So a handshake continuation or inbound frame from a replaced or destroyed connection neither writes nor applies state.

Document and awareness observers run outside the actor, and native unsubscribe does not wait for callbacks already running. Each callback registers with an observer ingress before encoding, appends its frame, then unregisters. `destroy()` cancels the observers and closes the ingress. It then awaits the callbacks that registered, using a continuation rather than a blocking wait on the actor. Only then does it take their frames, ahead of the removal. A callback that the native layer dispatched but that has not yet run its first statement when the ingress closes is skipped. Closing that window needs native unsubscribe to report completion. Actor-originated frames first flush already observed frames, keeping observation order.

The queue holds at most 1024 frames. A newer awareness frame replaces queued awareness frames whose clients it covers, so a slow socket sends only the latest state. Document updates cannot be dropped individually. Exceeding the capacity therefore fails the connection: the queue is discarded and the provider reconnects, and sync step 1 and 2 restore document state.

`destroy()` clears local awareness even when it is already null. The clear advances the local clock and sends a `null` update at that clock, consistent with the repeated-null behaviour in ADR-0026. JavaScript `destroy()` calls `removeAwarenessStates`, which does nothing for an absent local state, and detaches its update listener before `awareness.destroy()` sets null again. So JavaScript sends nothing in that case. The extra Swift update leaves receivers in the same state. y-protocols 1.0.7 receivers that already know the client still report it as removed, just as for any repeated local null.

`URLSessionWebSocketTask` writes the close frame after completed sends on the same connection. The end-to-end test traces raw frames on a real Hocuspocus server and checks that the `null` awareness frame arrives before the close. Hocuspocus server 4.x removes a closed connection's awareness clients as soon as the close arrives, even if earlier messages are still waiting on asynchronous hooks. So the server may broadcast its own cleanup removal before it applies the client's `null` update, as it can for the JavaScript provider.
